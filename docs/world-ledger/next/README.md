## 已有能力与实施前提

已接入七名具名角色、普通攻击/招架、角色体积、道具交易/装备/救助/搜刮、个人目击/举报、具名追捕、药包交还及存档。历史验证属于对应旧提交，不能自动证明本次性能修改或未来社会系统已通过。

基线仍存在以下边界，任务需明确解决：

1. `living/config.js` 引用旧案例的 NPC 固定坐标；`createLivingScene.js` 初始化要求所有出生点已加载，闲置时还会读取旧 home。
2. `navigation.worker.js` 仍调用 1,800 节点的 `localRoute`；`movementQuery.js` 拒绝未加载区域。将搜索移到 Worker 并不等于具备跨城路线。
3. `living/persistence.js` 要求角色集合与 `LIVING_NPCS` 完全相同；`runtime.js` 对完整配置和道具目录做签名校验。直接加 NPC/道具会破坏恢复。
4. 昼夜时间是循环的 0—24 小时，玩法时钟是递增毫秒；日程、跨日工资和到期事件需要统一映射。
5. 案件查询缓存基于不可变快照；举报、增援和部分任务仍绑定 `guard`、`guard-2`、`resident-1` 等固定 ID。
6. 活跃账本有限，临近容量会停机。不能用逐帧写日程、每秒追加饥饿事件、删日志或直接提高上限来支撑长期模拟。

## 实施顺序

编号对应之前讨论的 12 项能力；执行顺序按依赖安排，不要求机械地从 1 做到 12。

| 阶段 | 卡片顺序 | 阶段完成后玩家能感受到什么 |
| --- | --- | --- |
| P0 城内分布 | P0-01 → P0-02 → P0-03 → P0-04 | 商街买药、住宅救人、府衙办事，跨区来往可靠 |
| P1 日常基础 | 12-A → 02-A → 01-A → 01-B → 02-B → 10-A | 人有住处、店会开关门、工作可被打断并恢复 |
| P2 有事可做 | 07-A → 06-A → 07-B → 06-B → 10-B | 找人和送货可接、可放弃，有真实交付与结果 |
| P3 相互依赖 | 03-A → 03-B → 04-A → 04-B → 12-B | 居民互相传话、购货补货，世界能跨多日运行 |
| P4 社会与牵挂 | 05-A → 05-B → 08-A → 08-B → 09-A → 09-B | 势力办事有资源、玩家取得资格、冲突可以善后 |
| P5 长期体验 | 11-A → 11-B → 12-C | 平静生活与事件交替，远近状态连续、规模有依据 |

若新功能所需依赖尚未完成，先完成依赖；允许继续与之无关的卡片。每张卡形成独立可审阅改动，不把 12 项作为一次提交。

## 12 项范围一览

| 项 | 本轮明确要实现 | 后续再扩展 |
| --- | --- | --- |
| 01 生活目标 | 日程、吃饭/休息/工作、事务优先级、行动恢复 | 婚育、复杂心理模型 |
| 02 地点用途 | 居住/经营/值守绑定、营业时间、场所交互权限 | 完整室内和复杂门锁物理 |
| 03 人际关系 | 有方向的关系、有限传播、承诺的后果 | 自动生成庞大家族史 |
| 04 生计供需 | 药品/干粮、实际购货消耗、有限补货、工资 | 全产业链和动态宏观定价 |
| 05 势力规则 | 3 类组织、职责与资源、案件处理和申请援助 | 地盘战争、政治模拟 |
| 06 自发事件 | 真实需求产生委托、NPC 也能接单、到期和收尾 | 自动长篇主线 |
| 07 参与办法 | 问人问事、找人带话、接受/兑现/拒绝委托 | 通用自由文本谈判 |
| 08 成长牵挂 | 社会资格、住处使用权、技能入门的具体用途 | 完整门派与技能树 |
| 09 恢复善后 | 伤后恢复、停业代班、财物处理、失败后继续 | 生育与跨世代继承 |
| 10 信息表达 | 固定地点导航、个人知识对话、生活状态与后果提示 | 全量配音与新建模 |
| 11 日常节奏 | 正常生活小事、通知优先级、有限打扰和冷却 | 强制改写事实的剧情导演 |
| 12 长期运行 | 版本迁移、统一时钟、历史归档、远近模拟一致 | 数千 NPC、联机同步、离线补算 |

每张卡记录：`状态 / 实际修改文件 / 提交 / 静态审阅 / 实际运行证据 / 待处理问题`。完成状态使用 `TODO`、`IMPLEMENTED`、`REVIEWED`、`RUNTIME_VERIFIED`，分别陈述，不用“代码写完”替代实际验收。

当前根规则为“不运行测试、不运行 build、不运行 lint”。本次同步与计划编写不运行这些命令。历史上的战斗测试例外不能推定覆盖未来全部任务。卡片内的验收描述是将来需要观察的结果，执行时遵守当时的规则和用户明确授权；没有运行就如实记录，不为每个小改动反复要求用户确认。

低思考强度的执行方式建议：一次给一张边界清楚的卡片，附上依赖结果和完成标准。版本迁移、导航数据生命周期、资金事务、归档与多域时序列为集中审阅点；不能用提示词长度保证这些改动正确。任务描述方式参考 [OpenAI 官方提示词说明](https://learn.chatgpt.com/docs/prompting)，本项目拆分及风险判断来自实际代码审阅。
